How this workbench works
A plain-language guide to what we're testing, how to run it, and how to read the numbers.
What we're researching
There are two ways to build a live speech interpreter. One is a single AI model that listens in one language and speaks in another — one sealed box. The other is an assembly line: one service turns speech into text, another translates it, a third speaks the translation. The sealed box is simpler; the assembly line lets you swap any part. This workbench runs both on identical recorded input and measures which is faster, cheaper, better sounding, and easier to control — so the choice rests on data instead of vendor marketing.
Live vs Replay — the two modes
Live is a real interpreter: speak, hear the translation, up to five minutes, one architecture at a time. It's how you experience the product — and how conversation-length effects (creeping delay, rising cost) are measured. Its metrics are saved; its audio is discarded.
Replay is the laboratory. Record a clip once (or use the built-in corpus), then run that exact same audio through any configuration you like. Because the input is identical every time, two runs are directly comparable — that's what makes the measurements trustworthy. Nothing in Replay ever autoplays; you listen on demand.
Three things to keep straight: a Recording is an input (what was said), a Run is one execution of a Recording through one configuration, and a LiveSession is a real conversation's metrics. Live sessions and Runs are never compared — different inputs, no shared basis.
The three arms
An "arm" is a named, frozen recipe. You never label a run yourself — the app derives the tag from what you actually configured. Assemble Arm B's exact recipe and your run is an Arm B run; deviate anywhere and it's tagged "ad-hoc" (explorable, but never counted as experimental evidence).
Arm ARealtime — the sealed box. OpenAI's voice-to-voice model does everything internally. We can't see inside; we can only time the whole thing.
Arm BCascade, all-OpenAI — the assembly line built entirely from OpenAI parts. A and B share a vendor, so any difference between them is caused by the design, not the company.
Arm CCascade, one part swapped — identical to B except the voice stage, which uses ElevenLabs. Exactly one difference, so whatever changes between B and C is caused by that one swap.
The experiments
1 · Does the design itself cost speed? Arm A vs Arm B on the same recordings, same vendor. This is the headline result.
2 · What does swapping one part buy? Arm B vs Arm C — only the voice stage differs, so the delta is cleanly attributable.
3 · What happens over a long conversation? Measured in Live, not Replay. The sealed box re-reads the whole conversation on every turn, so its cost per minute climbs; the assembly line stays flat. A "trimmed" setting deletes history each turn to prove the slope comes from billing, not from voice-to-voice itself.
4 · What about a less common language? Cantonese, as a case study against the same vendors. Realtime doesn't list it; we run it anyway to see how it fails — the transcript can look right while the audio is actually Mandarin. Only a native speaker's ear catches that, which is why blind scoring is playback-only.
These tracks are never mixed: a Cantonese finding is never evidence about Spanish speed. Each result screen names its own question and its own data.
How to use it
1. In Live, press Start microphone and speak — the translation plays back automatically. Switch architecture or language mid-conversation; switches wait for your sentence to finish.
2. In Replay, pick a Recording (or record a clip, up to a minute), choose an architecture — and for the cascade, a model for each of the three stages. The panel tells you live whether your recipe matches a named arm.
3. Press Run to execute once, or Batch sweep to run a whole matrix unattended (~$4, ~68 minutes) — it shows progress and can be cancelled without losing completed runs.
4. With two or more runs of the same Recording, use Compare blind: listen to both without knowing which is which, rate adequacy and fluency, then see the reveal. Scores go into the ledger.
How to read it
The stage timings show where the time goes, in labelled milliseconds. The cascade shows all five steps; Realtime shows three, with its big middle one marked opaque — the sealed box. When something breaks, the cascade names the failed stage; Realtime can't. That difference is itself a finding.
p50 / p95 — the typical delay and the bad-day delay. Half of responses are faster than p50; 95% are faster than p95.
Cost per minute — what a minute costs in provider fees. In Replay it's a snapshot; the conversation-length screen shows whether it climbs.
Provenance lines — the small mono text under each title says exactly which recordings, how many repeats actually completed ("4 of 5"), and which settings produced the number. A number without that line is just a claim.
"Illustrative" badges — every figure in this mock is a realistic placeholder, not a measurement. The real app shows "No runs recorded" until a sweep has actually run.
